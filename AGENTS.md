# Commit attribution

- Do not add a `Co-Authored-By` trailer naming an AI tool or model (Claude, Codex or others) to any Git commit message.
- Do not add equivalent AI authorship or "generated by" attribution elsewhere in commit messages.
- Preserve the repository's configured human author and committer identity.
- Apply these rules to new commits, amended commits, and rewritten commits.

# Cadence, tests, history and worktrees

- Follow sections 2, 3, 6 and 7 of `docs/APP_WORKFLOW.md`, with this repository's tests in place of an app's. The rest of this file adds what is specific to frost_ui.

# Library scope

- frost_ui is shared by several apps. Shared adaptive, motion, material and layout behavior lives here, so apps compose components instead of branching on size class or platform themselves.
- Prefer a default or composition to a new public parameter with a single caller; merge or remove parameters that lose their purpose.
- Platform capability (custom title bar, Mica, window state) is reported by frost_window from the actual OS state, and apps read it from there.

# Documents

- Docs state current rules and API facts, not progress, test counts, commit ids or stage status; git and the code are the record.
- Comments and test names describe behaviour, not stage, batch or audit codes.

# App change requests

- Apps do not edit frost_ui's source, tests or tools. What an app needs from frost_ui arrives as a request in `docs/requests/`; its `README.md` holds the format, the statuses and the maintainer steps.
- Work on requests only in a maintainer session the owner starts. Take every `open` request in that pass unless the owner narrows the scope.
- A default or geometry change reaches every app. Weigh it against a new parameter, and make it only with a `--dependents` check and the owner's confirmation.
- Do not edit app repositories. At the end, list the apps whose workarounds can now be replaced.

# Checks

- At a checkpoint, run `dart tool/affected_tests.dart <base> --run`, where `<base>` is the previous checkpoint's commit. It analyzes the changed libraries and their direct importers, runs the tests that use what the changed libraries declare, and runs the script test of a changed tool. Add `--consumer <app directory>` for each app whose request or usage the change touches, and `--dependents` only when the change alters a default or geometry that every caller sees.
- Run tests through `affected_tests.dart` or with named test files; the PreToolUse hook in `.claude/settings.json` blocks a bare `flutter test` / `dart test`.
- The library health gate runs inside `affected_tests.dart`; its spec is `tool/library_health/README.md`. If it reports growth, stop and report it.
- A full run happens when the owner asks for one, usually before a release: `dart tool/affected_tests.dart --all --run`. Baseline tests render every environment and fail on layout overflow.
- frost_ui changes need no screenshots; text overflow is checked by tests.

# Dart imports and dependency direction

- Inside a package's `lib/`, use relative imports/exports for that same package. Use `package:` for other packages and when tests or tools import `lib/`; never enter or leave `lib/` with `../lib/` or a relative escape.
- Import the defining internal library instead of the package's public barrel. Keep `frost_ui.dart` as the app-facing export surface. Re-export a moved type there (or from its existing entry point) so import cleanup does not change the supported public API.
- Order directives with Dart's `directives_ordering` rule. `prefer_relative_imports` and `avoid_relative_lib_imports` enforce the path boundary.
- Configuration types, shared dimensions and inherited layout data belong below painting, controls and page layouts. They must not import a renderer/widget merely to obtain a data type, constant or window classification.
- A basic control must not import a list/page because its row variant lives in the same file. Keep the mark/control separate from the component that composes it with a row. Row variants may depend on both.
- `FrostApp` and `FrostTheme` are composition roots: their component/route integration imports are intentional. Routing transitions, skeleton adapters and composed controls are not low-level utilities merely because of their directory names.
- Review cycles by responsibility. Small, cohesive context/configuration or surface/geometry pairs can be valid; do not add forwarding interfaces, global registries or duplicated constants only to make the import graph acyclic.
